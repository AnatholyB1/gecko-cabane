## Summary

The phase is mostly glue on top of mature pieces already in the repo. Vercel Cron is available on every plan, Hobby is limited to one run per day with +-59 min precision; `0 4 * * *` therefore fires between 11:00 and 11:59 Krabi, which fits D-05 and the J+1 11h wording. Cron calls are GET, send `Authorization: Bearer $CRON_SECRET` when that env var exists, are best effort, may be delivered twice or missed, and are not retried [CITED: vercel.com/docs/cron-jobs/manage-cron-jobs]. This makes the D-06 design (claim a row with a conditional update, then send) and D-07 bounded catch-up exactly the pattern Vercel recommends (idempotent, reconciliation-based).

Two findings change the plan. (1) `gecko_reservations.id` is an `integer` (see `gecko_create_reservation` returning `reservation_id integer`), not a UUID, so D-14's "opaque UUID" does not exist yet. Using the integer as `rid` would let anyone enumerate `rid=1..N` and flip `review_clicked_at` (suppressing reminders) and probe locales. Migration 014 must add a `review_token uuid not null default gen_random_uuid()` (unique) column and `rid` must be that token. (2) The three alias paths cannot be plain `next.config` redirects, because the rid-to-locale rule (D-10) needs a DB lookup; they must be tiny Route Handlers (`src/app/review/route.ts`, `avis`, `bewertung`) that 307-redirect to `/{locale}/review`, with an early pass-through in `src/middleware.ts` (otherwise next-intl would rewrite `/review` to `/fr/review`).

The Google `writereview?placeid=` link and the TripAdvisor `UserReviewEdit` link are both undocumented by the vendors; they work in practice, with reported regional/browser flakiness for the Google one. Plan a manual device test by the owner before 1 Nov and centralize both URLs in `src/utils/seo.ts` so they can be swapped (e.g. for the `g.page/r/.../review` short link copied from the GBP dashboard).

**Primary recommendation:** Pure `selectReviewInvitations(rows, nowUtc)` function (Vitest-tested) + one cron route that claims rows with conditional updates, + alias Route Handlers + `review_token` column; generate print PDFs with `qrcode` (matrix) + `pdfkit` (vector rects, standard fonts) in a committed script.

### Pattern 1: Cron route (secured, idempotent)
```ts
// Source: https://vercel.com/docs/cron-jobs/manage-cron-jobs
export const dynamic = 'force-dynamic'
export const maxDuration = 60 // [ASSUMED] ample for dozens of emails

export async function GET(request: NextRequest) {
  const cronSecret = process.env.CRON_SECRET
  if (!cronSecret || request.headers.get('authorization') !== `Bearer ${cronSecret}`) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  // never redirect: cron does not follow 3xx
}
```
Keep `!cronSecret` fail-closed (matches Vercel's own example). Use `crypto.timingSafeEqual` optionally.

### Pattern 2: Krabi date math (no library)
Krabi is UTC+7 with no DST, so add a fixed 7h offset. `reservation_date` is a `date` string, so compare strings or use UTC midnight arithmetic.
```ts
const KRABI_OFFSET_MS = 7 * 3600_000
export function krabiToday(now: Date): string {
  return new Date(now.getTime() + KRABI_OFFSET_MS).toISOString().slice(0, 10)
}
export function addDays(ymd: string, n: number): string {
  const [y, m, d] = ymd.split('-').map(Number)
  return new Date(Date.UTC(y, m - 1, d + n)).toISOString().slice(0, 10)
}
// invite window: date in [addDays(today,-3), addDays(today,-1)]
// remind window: date in [addDays(today,-7), addDays(today,-5)]
```
Note `reservation_date` strings compare lexicographically correctly (ISO). Cron fires 11:00-11:59 Krabi, i.e. 04:00-04:59 UTC, same Krabi calendar day, so `today` is stable. J+1 = `reservation_date === today-1` on a normal run; the 3-day window is only catch-up for a missed run.

### Pattern 3: Atomic claim before send
```ts
const { data: claimed } = await admin
  .from('gecko_reservations')
  .update({ review_email_sent_at: new Date().toISOString() })
  .eq('id', r.id)
  .is('review_email_sent_at', null)
  .in('status', ['confirmed', 'completed'])   // re-evaluate eligibility at claim time (D-09)
  .select('id')
if (!claimed?.length) continue                  // someone else (duplicate run) got it
const res = await resend.emails.send(payload, { idempotencyKey: `review-invite-${r.id}` })
if (res.error) {                                // release so tomorrow's catch-up retries (D-07)
  await admin.from('gecko_reservations').update({ review_email_sent_at: null }).eq('id', r.id)
}
```
Reminder claim: `.is('review_reminder_sent_at', null).is('review_clicked_at', null)`.

### Pattern 4: Alias Route Handler + middleware pass-through
```ts
// src/app/avis/route.ts (review/ and bewertung/ identical with a different hint)
export const GET = (req: NextRequest) => handleReviewAlias(req, 'fr')
// shared: rid(token) -> locale via createAdminClient; else hint; else Accept-Language; de|sv -> en
// return NextResponse.redirect(new URL(`/${locale}/review?${qs}`, req.url), 307)
```
In `src/middleware.ts`, add before the Supabase work (like `/monitoring`):
```ts
if (pathname === '/review' || pathname === '/avis' || pathname === '/bewertung') return NextResponse.next()
```
Without it, next-intl (`localePrefix: 'always'`, `localeDetection: false`) rewrites/redirects `/review` to `/fr/review` and the handler never runs. Static `app/review/route.ts` wins over the dynamic `[locale]` segment. Update `tests/middleware-matcher.test.ts` accordingly (it reads source text).

Precedence recommended: `rid` locale > alias hint (`/avis`=fr, `/bewertung`=de->en, `/review`=none) > Accept-Language (first of fr/en found, `de`->`en`) > `en`. This satisfies REV-01 ("redirigent selon la langue") and D-10. Use 307 (temporary, not cached; the result varies per request). Do NOT reuse a 308 here (browser-cached forever; see the existing comment in `next.config.ts`).

### Pattern 5: `/[locale]/review` page
- `generateMetadata` must NOT use `buildPageMetadata` (it emits canonical + hreflang). Return `{ title, robots: { index: false, follow: false } }` only (D-11). Do not add to `PUBLISHED_PAGES` or the sitemap.
- Read `searchParams` (async in Next 16) for `rid`, `src`; the page is then dynamic, so the click write runs on every request. Validate `rid` against a UUID regex before querying; update `review_clicked_at = now()` where `review_token = rid and review_clicked_at is null`. Wrap in try/catch: a DB failure must never block the buttons.
- Buttons are plain `<a href target="_blank" rel="noopener noreferrer">`. Preserve `src` only in the page URL (D-13).
- Text via `getTranslations({locale, namespace: 'review'})`; add the namespace to `messages/fr.json` and `en.json` (tests/i18n.test.ts parity; tests/i18n-hardcoded.test.ts guards literal strings in `[locale]`).

### Anti-Patterns to Avoid
- **Integer `rid`:** enumerable; use a random token column.
- **Marking `sent_at` after the send:** a crash or double delivery between send and mark yields duplicates; claim first.
- **Computing "today" with the server's local timezone:** Vercel runs UTC; use the fixed +7h helper.
- **`next.config` redirects for the aliases:** cannot select locale from `rid`.
- **Permanent (308) redirect for aliases:** cached forever by browsers.
- **Calling `buildPageMetadata` on `/review`:** would emit hreflang/canonical (violates D-11).

## Common Pitfalls

### Pitfall 1: Hobby cron drift vs. wording "11h"
**What goes wrong:** Email arrives 11:00-11:59 Krabi, and the admin no-show window (D-03) "until 11h" may be cut short by up to an hour.
**How to avoid:** Display the deadline in admin as "avant 11h (Krabi) le lendemain; l'envoi peut avoir lieu entre 11h et 12h"; encourage marking no-shows the same evening. On Pro, precision is per-minute.

### Pitfall 2: Email security scanners trigger `review_clicked_at`
**What goes wrong:** Outlook SafeLinks / antivirus / link previewers GET the URL, marking it "clicked" and suppressing the J+5 reminder for guests who never opened it.
**Why:** D-13 writes on server render. **How to avoid:** accept (the tracking is deliberately minimal), document it; optionally skip the write when `user-agent` matches obvious bots. Flag as known limitation; do not over-engineer.

### Pitfall 3: Enumerable `rid`
See Summary. Use `review_token uuid`. The admin GET (`select *`) will return the token to admins only; that is fine but never to the public API. Verify `GET /api/reservations` select list so the token is not served unauthenticated.

### Pitfall 4: Duplicate / missed cron delivery
Handled by conditional update claim, catch-up window, and Resend `idempotencyKey` (key per reservation and kind: `review-invite-<id>`, `review-reminder-<id>`; Resend keys expire after a retention period [ASSUMED 24h], so the DB claim is the primary guard).

### Pitfall 5: Resend rate limit and failures
Send sequentially (default account limit about 2 req/s [ASSUMED]); volume is tens per day. On `res.error`, release the claim and `Sentry.captureException` (pattern in `reservations/route.ts`). Never throw out of the loop; return a JSON summary `{ invited, reminded, skipped, failed }` (no PII).

### Pitfall 6: Middleware intercepting aliases
Covered; update the matcher/pass-through test. Also the cron route lives under `/api`, which the middleware already bypasses for i18n (it still calls `getUser()`, harmless).

### Pitfall 7: Google review link reliability
`search.google.com/local/writereview?placeid=` is undocumented; reports of failures in the EU/some browsers and that it redirects to sign-in even for a fabricated Place ID [CITED: localsearchforum.com threads, quickseo.ai via web search; LOW-MEDIUM]. Mitigation: owner tests on iOS and Android; keep the URL in one constant; fallback is the `g.page/r/<id>/review` link shown in the GBP dashboard ("Ask for reviews"), which OPS-01 browser session can copy.

### Pitfall 8: Consent/legal classification of the review email
Some jurisdictions (notably Germany) treat unsolicited satisfaction/review-request emails as advertising requiring consent [ASSUMED, not verified in this session]. D-02 does not require `marketing_consent`. Raise with the owner (see Open Questions); mitigation is cheap: transactional tone, one reminder max, no promo content, mention reservation context.

```js
import QRCode from 'qrcode'
import PDFDocument from 'pdfkit'
const qr = QRCode.create('https://geckocabanerestaurant.com/review?src=qr', { errorCorrectionLevel: 'M' })
const n = qr.modules.size, data = qr.modules.data   // Uint8Array, 1 = dark
function drawQr(doc, x, y, sizeMm) { const cell = sizeMm * 2.8346 / n
  for (let r = 0; r < n; r++) for (let c = 0; c < n; c++)
    if (data[r * n + c]) doc.rect(x + c * cell, y + r * cell, cell, cell).fill('#0D1F17') }
```

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (cron only) | Bearer `CRON_SECRET`, fail closed |
| V3 Session Management | no | -- |
| V4 Access Control | yes | Service role only in cron + click mark with justification comment; admin badge via existing admin GET; `review_token` never in public responses |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unauthenticated call to cron route | Spoofing | Bearer check, 401, no work done |
| `rid` enumeration / click-flag tampering | Tampering/Info disclosure | Random UUID token, `is null` conditional update, no data echoed |
| Open redirect via alias params | Tampering | Redirect target built from whitelisted locale and fixed path; forward only whitelisted query keys (`rid`, `src`) |
| Header/HTML injection in email | Tampering | `escapeHtml` on name; `stripLineBreaks` for subject (existing helpers) |
| Duplicate email spam (double cron) | DoS (reputation) | DB claim + idempotency key + reminder cap |
| PII in logs / response | Info disclosure | Cron response returns counts only; Sentry gets ids, not emails |
