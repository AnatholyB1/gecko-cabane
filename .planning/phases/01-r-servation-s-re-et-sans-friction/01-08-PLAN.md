src/utils/anti-bot.ts (pure):
- `MIN_FILL_MS = 3000`, `MAX_FILL_MS = 24 * 60 * 60 * 1000`
- `isHoneypotFilled(value: unknown): boolean` -> typeof value === 'string' && value.trim() !== ''
- `checkFillTime(startedAt: unknown, now: number): boolean` -> number, finite, startedAt <= now, now - startedAt >= MIN_FILL_MS, now - startedAt <= MAX_FILL_MS

src/utils/rate-limit.ts:
- `RATE_LIMITS = { ip: { limit: 5, windowSeconds: 3600 }, email: { limit: 3, windowSeconds: 86400 }, phone: { limit: 3, windowSeconds: 86400 } }` (D-08)
- `getClientIp(h: Headers): string | null` -> x-vercel-forwarded-for, then x-real-ip, then first x-forwarded-for entry, trimmed; null if none
- `hashKey(kind: 'ip' | 'email' | 'phone', value: string, secret: string): string` -> `${kind}:` + HMAC-SHA256 hex of value (email lowercased) with node:crypto createHmac
- `checkReservationRateLimits(admin: SupabaseClient, ids: { ip: string | null; email: string; phone: string }): Promise<{ limited: boolean }>` -> reads process.env.RATE_LIMIT_SECRET (missing -> Sentry.captureMessage + `{ limited: false }`), calls `admin.rpc('gecko_rate_limit_hit', { p_key, p_limit, p_window_seconds })` for ip (if not null), email, phone sequentially; any RPC error -> Sentry.captureException and treat that check as allowed; returns limited true if any call returned `false`

SQL: `public.gecko_rate_limit_hit(p_key text, p_limit int, p_window_seconds int) returns boolean` (true = allowed), fixed window `to_timestamp(floor(extract(epoch from now()) / p_window_seconds) * p_window_seconds)`, `insert ... on conflict (key, window_start) do update set hits = r.hits + 1 returning hits`, opportunistic purge (`random() < 0.02` -> delete rows older than 2 days), security definer, search_path public, execute for service_role only.

429 messages: fr "Trop de demandes depuis votre connexion. Écrivez-nous directement sur WhatsApp : +66 81 958 5945." / en "Too many requests from your connection. Message us directly on WhatsApp: +66 81 958 5945."

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-36 | Denial of service | booking spam / slot saturation | mitigate | 5/h per IP, 3/day per email, 3/day per phone (D-08) + capacity cap (01-06) |
| T-01-37 | Spoofing | bots | mitigate | honeypot fake success + 3 s minimum fill time with 24 h ceiling (D-09) |
| T-01-38 | Spoofing | forged X-Forwarded-For | mitigate | prefer x-vercel-forwarded-for / x-real-ip (Vercel-controlled); no shared 'unknown' bucket |
| T-01-39 | Information disclosure | IP/email/phone stored for limiting | mitigate | HMAC-SHA256 with RATE_LIMIT_SECRET, purge after 2 days, RLS without policy |
| T-01-40 | Tampering | counter race | mitigate | single INSERT ... ON CONFLICT DO UPDATE RETURNING statement; verified on scratch DB in 01-09 |
| T-01-41 | Denial of service | rate-limit DB failure blocks real guests | accept | fail-open + Sentry alert (A8): losing bookings in high season is worse than a short unthrottled window |
| T-01-42 | Elevation of privilege | anon calling gecko_rate_limit_hit via PostgREST to reset/inflate counters | mitigate | execute revoked from public/anon/authenticated, service_role only |
