<root_cause>
## GECKO-CABANE-R (identified by code reading)

`upsertResendContact` in `src/utils/resend-contacts.ts` (lines 49-73) does:
1. `resend.contacts.create({ email, unsubscribed: false, properties, segments })`
2. on ANY create error (the error is discarded, never inspected or reported), it unconditionally calls `resend.contacts.update({ email, ... })`
3. on update error it reports `Resend contact upsert failed: ${updated.error.name}`.

The fallback assumes "create failed => the contact already exists". In SDK resend 6.28.1 (`node_modules/resend/dist/index.mjs` lines 602-617), `update` with an email is `PATCH /contacts/{email}`; for a contact that does not exist Resend answers `not_found`. So `not_found` proves the contact is NOT in Resend, which means step 1 failed for a reason other than "already exists", and that real reason is thrown away. The reported `not_found` is a masking symptom.

Why the same 11 contacts recur: they are ledger rows with `contact_synced_at = null` (creation failed at /api/newsletter/confirm). The cron retries exactly those rows every day (route.ts "2. Contact mirror"), the create keeps failing for the same persistent reason, update keeps returning not_found, and the row is never marked synced.

Plausible persistent create failures (the code cannot tell which, because it discards the error): the 6 custom contact properties (language, country, resident, source, consent_at, last_visit) were never created in Resend (`scripts/setup-resend-newsletter.mjs` is owner-gated; `docs/newsletter/RESEND-SETUP.md` section 3 explicitly says "Si une propriété manque, la création du contact échoue"), or `RESEND_SEGMENT_ID` points to a segment that does not exist. Task 1 step A checks both read-only; the code fix is the same either way: inspect the create error, look the contact up, only update an existing contact, and report the real create error.

Secondary weakness: the email is used as-is as the Resend key (create body and PATCH path). Mixed-case ledger emails can make the by-email lookup miss. Normalize with `trim().toLowerCase()` in all three helpers.

Consent issue in the same code: the update fallback always sends `unsubscribed: false`, so a cron retry could re-subscribe a contact that unsubscribed inside Resend. Only a fresh double opt-in (confirm route) may do that.

## GECKO-CABANE-S

`src/middleware.ts` matcher already excludes `*.png`, so the middleware never sees `/apple-touch-icon-precomposed.png`. The file does not exist in `public/` (only `apple-touch-icon.png`), so the App Router matches `src/app/[locale]` with `locale = "apple-touch-icon-precomposed.png"`. `[locale]/layout.tsx` calls `notFound()`, but layout and page render concurrently: `src/app/[locale]/page.tsx` line 570 passes the raw param to `<SocialProof locale={locale as SeoLocale} />`, and `src/components/SocialProof.tsx` line 26 runs `new Intl.NumberFormat(locale)` -> RangeError. There are no nested dynamic segments under `[locale]` (checked), and the layout already exports `generateStaticParams()` returning the 4 locales, so `export const dynamicParams = false` 404s every other value before any render. Defense in depth: pass `toSeoLocale(locale)` to SocialProof, and serve the icon iOS asks for.
</root_cause>
