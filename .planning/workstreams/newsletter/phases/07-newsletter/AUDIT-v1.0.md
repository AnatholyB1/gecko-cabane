## Pass 1 and 2: findings (code review, security, compliance)

HIGH
- H1 | src/app/api/cron/newsletter-sync/route.ts:64-65 (also :96 send log, and newsletter-legacy-confirm/route.ts:57) | The cron reads the whole append-only consent ledger with `.select('*')` and no pagination or order. Supabase/PostgREST caps a response at `max_rows` (1000 by default on hosted projects; no supabase/config.toml in the repo to prove otherwise). The ledger gets one row per subscribe attempt, per reservation opt-in and per withdrawal, so it will pass 1000 rows. Once truncated, withdrawal rows can be missing from the slice, `resolveActiveSubscribers` then treats an unsubscribed person as active, and the cron mails them (PDPA/GDPR breach, the exact thing the ledger exists to prevent). Same truncation on `gecko_newsletter_sends` makes the 1 campaign/30 days cap and dedup blind (dedup is still saved by the unique key; the cap is not). | Page through with `.range()` in a loop ordered by `id` until a short page, or move the "active subscribers" resolution to a SQL view/RPC. Add a test with 1500 rows. Fail closed if a page count equals the cap.

MEDIUM
- M1 | src/app/api/cron/newsletter-sync/route.ts:21,37-38,172-221 | Budget of 80 calls with a 600 ms pause each is 48 s of sleeping alone, plus Supabase insert + Resend latency per send; `maxDuration = 60`. A full first campaign run (hundreds of eligible contacts, 80 per run) will probably be killed by the platform mid-loop. The claim row is inserted before the send, so a kill between claim and send leaves a `gecko_newsletter_sends` row without any email: that contact is silently skipped for the whole period (year). Safe direction (no double send) but silent loss. | Lower the budget to about 40 or raise maxDuration if the plan allows; use Resend batch send; write the claim with a `status` (claimed/sent) so stale claims older than 15 min are retried.
- M2 | src/app/api/cron/newsletter-sync/route.ts:203-220 | If `resend.emails.send` throws after Resend accepted the message (timeout), the claim is deleted and the next run sends again: duplicate campaign mail, and the second one would also defeat the monthly cap logic. | Pass an `Idempotency-Key` (`${kind}:${period}:${email hash}`) to Resend on every send, and keep the claim on ambiguous errors (timeout), releasing only on explicit API error.
- M3 | src/app/api/newsletter/subscribe/route.ts:73-80 + src/utils/newsletter-ledger.ts:91-98 | `decideSubscribeAction` only suppresses repeat mails for a recent pending row. A `withdrawn` address (someone who unsubscribed or complained) and a pending row older than 24 h both return `create`: any third party can make us mail a confirmation to a person who explicitly withdrew, up to the email limit (3 per 24 h, rate-limit.ts:429-432) and the IP limit (5 per hour per IP, so rotating IPs multiplies it). Each attempt also inserts a new consent row. | For a withdrawn address, allow re-subscription at most once per 7 days (or require the confirm link to be requested from the same session); lower the per-email limit to 1 per 24 h; do not insert a new row until confirmed (keep a single pending row and re-send).

## FIXES (branch fix/v1.0-phase7)

No flag or env value changed (NEWSLETTER_CAMPAIGNS_ENABLED untouched). No migration needed. No push, deploy, DB write or real email. Tests mock Supabase and Resend.

- H1 FIXED. `src/utils/paginate.ts` (`fetchAllPages`): 500-row range pages ordered by id, exact count required, throws `TruncatedReadError` if the rows received do not reach the count (server max_rows below the page size, missing count, page cap). Used for the ledger and `gecko_newsletter_sends` in newsletter-sync and for the ledger in newsletter-legacy-confirm. On any failure the cron returns 500 before planning or sending (fail closed). Tests: `tests/newsletter-fixes.test.ts`, `tests/newsletter-cron-route.test.ts` (1500/1200 rows, withdrawal in the last row wins, capped read -> 500 and zero sends).
- M1 FIXED (loss window). A 50 s time budget (`hasTimeForSend`, checked BEFORE the claim insert) replaces the sole reliance on a call count; a contact is never claimed unless its send can finish before the deadline. Contact mirror loops use the same check. Remaining contacts are counted in `skipped` and picked up next day.
- M2 FIXED. Every Resend send now carries an `idempotencyKey` (`nl:<kind>:<period>:<sha256(email)[0..32]>`) in cron, legacy, subscribe and reservation paths. A thrown (ambiguous) send keeps the claim and is reported as `ambiguous`; only an explicit API error releases the claim for retry.
- M3 FIXED. `decideSubscribeAction`: any address with a withdrawal returns `skip_withdrawn` (uniform silent response, no mail, no new row); pending addresses get at most one mail per 24 h across all their pending rows and at most 3 in total (`skip_pending_cap`). Consequence to know: a person who unsubscribed cannot re-subscribe through the public form; the owner must handle that by hand. Per-email rate limit (rate-limit.ts) left unchanged.
- M4 FIXED (decision: send the double opt-in confirmation from the reservation path). `sendReservationOptInConfirmation` (called in the reservation `after()` block when the box was ticked) sends the same confirmation mail as the public form, only for a pending row, never to an address that ever withdrew or is already active, with the same 24 h and cap rules. No marketing mail is sent before the guest clicks confirm. The manual legacy job stays dry by default and unchanged in behaviour. Needs the owner to be aware: a confirmation mail now leaves automatically with each reservation that has the box ticked (requires NEWSLETTER_SIGNING_SECRET and RESEND_API_KEY, otherwise skipped).
- M5 DOCUMENTED, not changed (flag/ops decision belongs to the owner): run `?dry=1`, record `planned`, get written approval or set the flag to 0.
- L1-L9, I1-I3 DOCUMENTED, unchanged.
